\section{Phase I: Data Integrity Verification and Cleaning}
\label{sec:phase1_cleaning}

\subsection{Sanity checks}
\label{sec:phase1_sanity}

The final Phase I dataset is checked at three levels:
\begin{itemize}[leftmargin=*]
  \item window integrity: each of the ten projects has seven consecutive windows from eight frozen tags;
  \item row arithmetic: for every developer-window row, \texttt{churn} $=$ \texttt{added} $+$ \texttt{deleted};
  \item aggregation consistency: window totals equal the sums of the corresponding developer rows.
\end{itemize}

All 70 centralized windows pass these checks. No clean window has zero commits or zero churn. The all-account clean dataset
contains 1{,}118 developer-window rows, and the centralized window-total table contains 70 rows.

\subsection{Canonical identity}
\label{sec:phase1_dedup}

Developer identity is canonicalized during extraction using the key:
\[
(\texttt{project\_id}, \texttt{window\_id}, \texttt{author\_email})
\]
For each key, commits are aggregated by email address and a canonical \texttt{author\_name} is selected using the most frequent
non-\texttt{unknown} display name. The cleaning pass found no duplicate key groups in either the extended cohort or the centralized
dataset:
\begin{itemize}[leftmargin=*]
  \item extended dataset: 845 input rows, 845 clean rows, 0 duplicate groups merged;
  \item centralized dataset: 1{,}118 input rows, 1{,}118 clean rows, 0 duplicate groups merged.
\end{itemize}

\subsection{Bot labeling}
\label{sec:phase1_bots}

Automated accounts are retained in the clean all-account dataset and marked with \texttt{is\_bot}. This makes the automation
policy visible and allows two populations to be reported:
\begin{itemize}[leftmargin=*]
  \item all-account outputs, used as the audit baseline for total repository activity;
  \item human-only outputs, used as the primary population for M3 cadence and M4 ownership/concentration.
\end{itemize}

The centralized clean dataset contains 55 bot developer-window rows and 1{,}063 human developer-window rows. Bot accounts contribute
999 of 9{,}560 commits (10.45\%) but only 9{,}294 of 2{,}066{,}059 churn lines (0.45\%). This confirms that automation affects
commit-frequency and ownership/cadence interpretation more than aggregate churn magnitude.

\subsection{Known limitation: timestamp semantics}
\label{sec:phase1_author_date_lim}

Some commits included in a tag-to-tag revision range may have committer timestamps outside the tag-date interval. This can happen
when work was committed on a branch before it became reachable from a later tagged release. Churn, commit counts, and ownership
shares are computed from Git revision ranges and are not affected by this timestamp drift. Cadence features based on first/last
commit timestamps are more sensitive, so Phase II uses human-only commit counts and duration-normalized rates as the primary
cadence evidence and treats timestamp-derived active-day fields as sensitivity evidence.
