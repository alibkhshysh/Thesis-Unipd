\section{Phase III: Deterministic M4 and Hybrid Fabric PoC Design}
\label{sec:phase3_poc_design}

Phase III begins by freezing the selected signal as an implementation contract before writing verifier or chaincode code.
This avoids a common reproducibility failure in which the metric formula, rounding, evidence fields, and trust assumptions
change during implementation. The phase adds only new artifacts under
\path{Data,Outputs,Logs,Scripts/Phase 3 PoC/}; the Phase I, Phase II, and post-hoc inputs remain unchanged.

\subsection{Versioned metric policy and arithmetic audit}
\label{sec:phase3_metric_freeze}

The implementation identifier is \path{M4_DEVELOPER_CHURN_SHARE}.
The associated policy is \path{M4_DEVELOPER_CHURN_SHARE_POLICY}, version \texttt{1.0.0}.
Its canonical policy SHA-256 is:

The policy freezes the original extraction semantics: non-merge \texttt{git log --numstat} history, author email
(\texttt{\%ae}) as the canonical identity source, case-insensitive regex bot exclusion, all changed paths without a
source-language filter, and binary changes contributing zero textual churn. The PoC additionally requires linear Git
ancestry and uses the exact integer ppm formula in Section~\ref{sec:selected_metric_definition}.

An independent validator reconstructs developer churn, denominators, individual shares, top-one share, and Gini directly
from the human developer table. It then checks the frozen ownership tables and the Phase II C1 source values.

\subsection{Fabric platform profile}
\label{sec:phase3_fabric_profile}

The baseline freezes Hyperledger Fabric 2.5.15 from the 2.5 LTS line. The official Fabric test network is
Docker-Compose based and contains two peer organizations and an ordering organization; its documentation explicitly
positions it as an education and testing environment rather than a production
template~\cite{fabricTestNetwork,fabricRelease2515}. JavaScript and TypeScript chaincode are supported by the documented deployment
workflow~\cite{fabricDeployChaincode}. JavaScript is selected because the local environment already provides Node and Docker,
while no Go toolchain is installed.

The frozen network profile uses one peer for \texttt{Org1MSP}, one peer for \texttt{Org2MSP}, a single-node Raft orderer,
channel \texttt{mychannel}, default GoLevelDB state, and JavaScript chaincode \texttt{m4evidence}. Fabric Node libraries are
pinned at 2.5.8. Both organizations endorse writes, while \texttt{Org1MSP} is the authorized evidence submitter in the
baseline scenario.

Policy and manifest hashes use UTF-8 JSON with lexicographically sorted object keys, no insignificant whitespace, no
non-finite numbers, and no trailing newline in the hashed bytes. Dynamic values such as Fabric transaction ID, submitter
identity, and transaction time are excluded from the evidence manifest, so identical evidence produces identical manifest
bytes. The manifest does not contain its own hash; that SHA-256 commitment is placed in the ledger submission.

The chaincode derives a composite primary key from project, window, developer hash, metric, and policy version. It rejects an
existing key rather than overwriting evidence. Secondary composite keys support project and developer queries without requiring
CouchDB rich queries. A successful write emits \texttt{M4MetricEvidenceSubmitted}.

\subsection{Trust model and residual threats}
\label{sec:phase3_trust_model}

The baseline authorizes \texttt{Org1MSP} as verifier/submitter and requires endorsement from both organizational peers. Org2
therefore participates in ledger validation, but endorsement alone does not prove the numerator and denominator. An auditor
must retrieve bytes matching the artifact hash and replay the matching policy/verifier version.

Hash commitments detect changed bytes but do not guarantee availability. Canonical email hashing is pseudonymization rather
than anonymization and does not prove real-world control of the email. The frozen bot regex remains heuristic. Churn can be
inflated through meaningless edits, and the ledger makes such evidence replayable rather than automatically determining its
semantic value. These limitations keep the result correctly framed as one auditable evidence signal, not a self-sufficient
reputation verdict.

\subsection{Baseline integration fixture}
\label{sec:phase3_fixture}

The first integration fixture is the ancestral \texttt{urllib3\_W03} window from tag 2.4.0 to 2.5.0. It belongs to the primary
duration set, contains nine human developers, and exercises bot exclusion through one Dependabot identity. Human churn is
1,058 lines. The selected top contributor has numerator 325, exact share $325/1058=0.307183364839\ldots$, and deterministic
ledger value 307,183 ppm. The pinned fixture includes both 40-character commit hashes, the pseudonymous developer hash, policy
hash, bot context, supporting Gini, and expected rounding result.

The design validator checks all three schemas, local references, required fields, shared ledger constraints, policy constants,
and fixture values. It reports zero failures and emits canonical hashes for the policy, design, and schemas. This completes the
design gate used by the off-chain implementation in Section~\ref{sec:phase3_offchain_verifier}, the chaincode implementation
in Section~\ref{sec:phase3_chaincode_unit}, and the network evaluation in Section~\ref{sec:phase3_fabric_network}; all were
implemented against the same fixed contracts rather than evolving prose.
