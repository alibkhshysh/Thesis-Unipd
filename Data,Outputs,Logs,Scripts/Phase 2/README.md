# Phase 2 comparative evaluation and PoC metric selection

This phase compares the five candidate metric families under the thesis
decision framework and freezes the metric selected for the baseline
proof-of-concept. It consumes the centralized Phase 1 evidence without
modifying it, evaluates C1 stability, C2 interpretability, C3 gaming
resistance, C4 long-term suitability, and smart-contract feasibility, then
selects M4 developer churn ownership share.

Phase 2 writes only under this directory. The later post-hoc ancestry package
tests sensitivity to divergent release lines but does not replace these frozen
baseline results. Phase 3 consumes the selected M4 definition and independently
validates its arithmetic before implementation.

## Evidence boundary

The criteria do not all represent the same kind of evidence:

- C1 is calculated empirically from the frozen Phase 1 metric tables;
- C2 and C3 are structured, documented assessments under predefined rubrics;
- C4 combines structured scoring with measured lifecycle coverage from Phase 1;
- smart-contract feasibility is a separate 10-dimension implementation gate.

Consequently, the C1--C4 average is a comparison aid, not four equivalent
empirical measurements. The original Phase 2 tables are retained unchanged;
the paper-facing corrected decision figure is generated separately in Phase 3
and labels this value as a comparison average.

## Directory layout

- `scripts/` — C1--C4 analysis, feasibility scoring, and final selection
  freeze programs.
- `out/` — rubrics, detailed scores, empirical tables, decision inputs, and
  final M4 selection artifacts.
- `figures/` — the figures generated by the Phase 2 scripts.
- `logs/` — timestamped row counts, decision summaries, and completion records.

The scripts use Python with `pandas` and `matplotlib`. Run them from this
`Phase 2` directory so the default `../Phase 1`, `out/`, `figures/`, and
`logs/` paths resolve correctly.

## Reproduce the Phase 2 decision pipeline

The execution order matters because the feasibility step consumes the C1--C4
summaries and the selection freeze consumes the resulting decision inputs.
Rerunning a step rewrites its corresponding Phase 2 outputs and log.

### Step 1: C1 stability

```powershell
python scripts/analyze_c1_stability.py
```

The script treats the centralized Phase 1 `_all` files as immutable inputs. It
builds five window-level signals and three developer-rank signals, then writes:

- `out/c1_metric_window_values_all.csv`;
- `out/c1_metric_stability_by_project_all.csv`;
- `out/c1_metric_stability_overall_all.csv`;
- `out/c1_rank_input_values_all.csv`;
- `out/c1_rank_stability_pairs_all.csv`;
- `out/c1_rank_stability_by_project_all.csv`;
- `out/c1_rank_stability_overall_all.csv`;
- the three `figures/c1_*.pdf` plots.

The primary window population excludes the 22 Phase 1 windows shorter than
seven days; those windows remain available for sensitivity analysis.

### Step 2: C2 interpretability

```powershell
python scripts/score_c2_interpretability.py
```

This writes the five-dimension rubric, 25 detailed candidate scores, five-row
summary, and figure:

- `out/c2_interpretability_rubric_all.csv`;
- `out/c2_interpretability_scores_all.csv`;
- `out/c2_interpretability_summary_all.csv`;
- `figures/c2_interpretability_scores.pdf`.

### Step 3: C3 gaming resistance


### Step 4: C4 long-term suitability

```powershell

```

This checks the 10-project, 80-tag, 70-window lifecycle coverage and combines it

- `out/c4_lifecycle_coverage_all.csv`;
- `out/c4_metric_evidence_all.csv`;
- `out/c4_longterm_rubric_all.csv`;

### Step 5: smart-contract feasibility and combined decision inputs

```powershell
python scripts/score_smart_contract_feasibility.py
```

The feasibility gate evaluates 10 dimensions for each candidate and consumes
the completed C1--C4 summaries. It writes:

- `out/phase2_metric_comparison_all.csv`;
- `out/feasibility_rubric_all.csv`;
- `out/feasibility_scores_all.csv`;
- `out/feasibility_summary_all.csv`;
- `out/poc_candidate_decision_inputs_all.csv`;
- `figures/feasibility_scores.pdf`;
- `figures/poc_candidate_readiness_scores.pdf`.

The recorded feasibility gate leaves M2, M3, and M4 eligible. M4 is the
preferred candidate after the combined selection rule. M1 remains contextual,
and M5 is excluded from the baseline because it is a design extension without
the required issue/pull-request event dataset.

### Step 6: freeze the selected metric

```powershell
python scripts/freeze_poc_metric_selection.py
```

This step does not recompute C1--C4. It validates the decision-input and
feasibility tables, then freezes:

- `out/poc_metric_selection_all.csv`;
- `out/poc_metric_selection_rationale_all.csv`;
- `out/poc_metric_analysis_policy_all.csv`;
- `out/poc_metric_record_fields_all.csv`;
- `out/poc_metric_supporting_signals_all.csv`.

## Frozen selection result

The selected baseline is:

- metric family: `M4` ownership/concentration;
- signal: `M4_developer_share_churn`;
- name: developer churn ownership share;
- formula: `developer_human_churn / window_total_human_churn`;
- population: human-only Git authors after bot filtering and email-based
  identity canonicalization;
- window: a frozen consecutive semantic-version release window;
- primary Phase 1 source: `../Phase 1/out/ownership_dev_shares_human_all.csv`;
- selection status: `selected_for_baseline_poc`;
- feasibility exclusions: none.

The frozen selection package contains one selection row, six rationale rows,
eight analysis-policy rows, 13 proposed record-field rows, and five supporting
signal rows. Supporting context does not turn M1, M2, M3, or M5 into additional
on-chain reputation values for the baseline PoC.

## Validation snapshot

The Phase 2 logs record:

- C1: 350 window-signal rows, 50 project-stability rows, five overall rows,
  180 rank-pair rows, and no missing Phase 1 input stage;
- C2: five rubric dimensions, 25 score rows, and five summaries;
- C3: five rubric dimensions, 10 attack-surface rows, 25 score rows, and five
  summaries;
- C4: 10 project lifecycle rows, five metric-evidence rows, 48 primary windows,
  and 22 sensitivity-only windows;
- feasibility: 10 dimensions, 50 detailed score rows, five summaries, and five
  decision-input rows;
- final freeze: M4 selected with its rationale, policy, record shape, and
  supporting signals written successfully.

## Downstream lineage and limits

- `../Posthoc Validation/` audits whether each chronological release window is
  also an ancestral Git interval and reruns C1 on the eligible subset. It does
  not overwrite this phase or recalculate the frozen multi-criterion score.
- `../Phase 3 PoC/` independently validates the M4 arithmetic, freezes the
  evidence/ledger schemas and trust boundary, replays the Git evidence,
  validates chaincode locally, and tests the contract on a two-organization
  Fabric network.
- The selected M4 signal is an auditable engineering baseline, not a universal
  proof of developer quality or empirically complete gaming resistance.
